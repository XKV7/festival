# 🎰 CASINO ROYALE — 학교 축제 카지노 웹사이트

순수 HTML/CSS/JS + Firebase Realtime Database(CDN compat SDK)로 만든 정적 사이트입니다. 빌드 도구가 없으며 GitHub Pages에서 저장소 루트를 그대로 서빙합니다.

## 배포 절차 (GitHub Pages + Firebase만 사용)

### 1. Firebase 프로젝트 준비
1. https://console.firebase.google.com 에서 프로젝트 생성.
2. **빌드 → Realtime Database → 데이터베이스 만들기** (위치는 아무 곳, 규칙은 우선 테스트 모드).
3. **규칙** 탭에 `database.rules.json` 내용을 붙여넣고 게시. (축제 당일만 쓰는 임시 DB이므로 공개 읽기/쓰기. 행사 후 DB를 삭제하거나 규칙을 `false`로 바꾸세요.)
4. **프로젝트 설정 → 일반 → 내 앱 → 웹 앱 추가**(호스팅 체크 불필요) 후 `firebaseConfig` 객체를 복사.
5. 설정값 넣기 — 둘 중 하나:
   - **간단**: `js/firebase-config.js` 상단의 `firebaseConfig` 자리표시자를 복사한 값으로 바꿔 커밋. (`databaseURL` 필수)
   - **키를 저장소에 남기지 않기**: GitHub 저장소 **Settings → Secrets and variables → Actions → New repository secret**, 이름 `FIREBASE_CONFIG_JSON`, 값은 firebaseConfig를 JSON으로 (예: `{"apiKey":"...","authDomain":"...","databaseURL":"...","projectId":"...","storageBucket":"...","messagingSenderId":"...","appId":"..."}`). 배포할 때 워크플로가 자동으로 파일에 넣습니다.

### 2. GitHub Pages
1. 별도 설정 없이 워크플로가 Pages를 자동으로 켭니다. (자동 활성화가 안 되면 저장소 **Settings → Pages → Build and deployment → Source** 를 **GitHub Actions** 로 선택.)
2. `main` 브랜치에 푸시(또는 PR 머지)하면 `.github/workflows/deploy-pages.yml` 이 자동 실행되어 게시됩니다. **Actions** 탭에서 진행 상황을 볼 수 있고, 수동 실행은 Actions → Deploy to GitHub Pages → Run workflow.
3. 주소: `https://<GitHub아이디>.github.io/festival/` (Settings → Pages 에 표시됨). 이 저장소는 https://xkv7.github.io/festival/ 입니다.

### 3. 행사 준비
1. 계정 생성: 관리자 페이지(`admin-7c2e9f.html`, 스태프만 주소 공유)의 **계정 생성 / 삭제** 패널에서 개수와 시작 번호를 정해 만듭니다. PIN 은 4자리 무작위로 새로 만들어집니다. 이미 있는 번호는 기본적으로 건너뛰고, "기존 계정 덮어쓰기"를 체크하면 칩과 PIN 을 초기화하며 덮어씁니다. GitHub Actions 탭의 **Generate accounts** 워크플로로도 되며, 그쪽은 아티팩트 `accounts-csv` 에 목록이 남습니다. 계정 ID 와 PIN 목록은 정산표 내보내기로 CSV 로 뽑아 접수 데스크에 비치.
   - 계정 삭제는 표 맨 오른쪽 **삭제** 버튼, 전부 지우려면 패널의 **전체 계정 삭제**. 되돌릴 수 없으니 행사 중에는 쓰지 마세요.
2. 컴퓨터실 PC 8대에서 `https://<주소>/` 를 전체화면(F11)으로 열어 둠.
3. 학생은 계정 + PIN으로 로그인 → 로비에서 게임 → 종료 시 접수 데스크에서 정산(관리자 패널의 정산 처리).

## 하우스 조절기 (`js/balance.js`)
- **보유 칩을 1,500 ~ 3,900 범위로 끌어당김**: 범위의 중간값(`target` 2,700)보다 **적으면** 결과를 여러 번 뽑아 가장 좋은 것을, **많으면** 가장 나쁜 것을 채택합니다. 중간값에서 멀수록 뽑는 횟수가 늘어 끌어당기는 힘이 세지고, 범위 경계(1,500 / 3,900)에서 힘이 최대가 됩니다. 칩의 이동을 막는 것이 아니라 가중치만 조금씩 바꾸는 방식이라, 범위를 넘어가는 판도 나오지만 오래 플레이하면 이 범위로 돌아옵니다.

  | 보유 칩 | 추첨 | 체감 |
  |---|---|---|
  | 1,650 이하 | 최선 5회 중 채택 | 잘 풀림 (초반 몰입) |
  | 1,800 | 최선 4회 | 유리 |
  | 2,100 | 최선 3회 | 조금 유리 |
  | 2,400 | 최선 2회 | 약간 유리 |
  | 2,600 ~ 3,290 | 1회 (자연 확률) | 게임 본래 확률 (엣지만큼 서서히 깎임) |
  | 3,300 ~ 3,999 | 최악 2회 | 잘 안 풀림 |
  | 4,000 이상 | 승률 10% 고정 | 거의 안 풀림 (내려올 때까지) |

- **조임 구간 4,000칩 — 모든 게임 승률 10%** (`squeezeFrom` / `squeezeWinRate`): 보유 칩이 4,000 이상이면 게임 본래 확률을 무시하고 **이길 확률을 10%로 고정**합니다. 이 판이 승리인지 패배인지를 판 시작할 때 한 번 정하고(90% 패배), 그 방향에 맞는 결과가 나올 때까지 뽑습니다.
  - 게임마다 본래 승률이 달라도(룰렛 48% · 하이로우 47% · 슬롯 39%) 조임 구간에서는 **8개 게임 모두 10%** 로 같아집니다. 실측: 룰렛 10.1% · 하이로우 9.9% · 슬롯 10.0%.
  - 블랙잭·바카라처럼 한 판에 두 번 뽑는 게임도 같은 `plan` 을 쓰므로 승·패 방향이 엇갈리지 않습니다.
  - 4,000 아래로 내려오면 바로 위 표의 일반 규칙으로 돌아옵니다. 사실상 4,000이 부드러운 천장 역할을 하고, 끌어당김 범위의 상한(3,900)이 그 바로 아래에 붙습니다(실측 종료 칩 p90 룰렛·하이로우 3,120 · 슬롯 3,680).
  - **우대 모드에서는 적용하지 않습니다.** 적용하면 우대로도 최고 보상까지 올라갈 수 없습니다.

- **크게 벌어본 사람은 구제 없음** (`richPeak` 6,300 / `richDrawsBelow` 1): 이번 로그인 세션의 최고 보유가 6,300을 넘은 적이 있으면, 목표 아래로 내려가도 끌어올림이 사라집니다. 하우스 엣지에 그대로 노출되어 **파산까지 갈 수 있습니다.** 최고 보유 기록은 `sessionStorage` 에 저장되어 게임 페이지를 옮겨 다녀도 이어집니다.
  - 처음 온 학생은 끝까지 구제를 받아 파산하지 않고, 크게 땄다가 잃기 시작한 사람만 바닥까지 갈 수 있습니다.
  - 파산하는 사람은 **6,300을 한 번 찍어봤던 사람**이고, 한 번도 못 찍은 사람은 끝까지 구제를 받습니다. `richPeak` 는 범위 상한(3,900)보다 한참 위에 둬야 합니다. 범위 바로 위에 두면 슬롯처럼 출렁임이 큰 게임에서 대부분이 한 번은 찍고, 그 뒤로 거의 전원이 파산합니다(상한이 3,300일 때 `richPeak` 3,800으로 실측 80%).
  - **범위를 넓히면 이 값도 같이 올려야 합니다.** 상한만 3,300 → 3,900으로 올리면 높은 쪽까지 올라가는 사람이 늘어 `richPeak` 6,000에서 슬롯 파산이 10% → 21% 로 뜁니다. 그래서 6,300으로 같이 올렸습니다.
  - 실측(시작 1,000 · 고정 베팅 200 · 300세션): 200라운드에서 파산은 슬롯 10% · 룰렛 0% · 하이로우 0%, 500라운드까지 계속하면 슬롯 37%. 룰렛·하이로우는 출렁임이 작아 6,300까지 올라가지 못하므로 사실상 파산하지 않습니다.
  - 칩에 비례해 베팅하는 평범한 플레이에서는 파산이 더 줄어듭니다(200라운드 슬롯 5%).

- **한 판 대박 방지 (배율 상한)**: 총 베팅액 구간별로 "총 지급 ÷ 총 베팅"이 상한 이상인 결과는 절대 나오지 않습니다. 베팅 100 미만은 제한 없음.

  | 총 베팅 | 금지 배율 | 총 베팅 | 금지 배율 |
  |---|---|---|---|
  | 500 이상 | 9배 이상 | 230 ~ 319 | 20배 이상 |
  | 470 ~ 499 | 10배 이상 | 190 ~ 229 | 25배 이상 |
  | 400 ~ 469 | 12배 이상 | 160 ~ 189 | 30배 이상 |
  | 320 ~ 399 | 15배 이상 | 120 ~ 159 | 40배 이상 |
  | | | 100 ~ 119 | 50배 이상 |

  예: 슬롯 7️⃣ 트리플(x50)은 베팅 100 이상에서 나오지 않고, 룰렛 단일 번호(x35)는 총 베팅 200 이상에서 맞지 않으며, 바카라 타이(x9)는 총 베팅 500 이상에서 나오지 않습니다.
- **한 판 획득 상한 4,700칩** (`BALANCE.maxWin`): 높은 배율이 터져도 한 번의 판·핸드에서 칩에 반영되는 순이익이 이 값을 넘지 않습니다.
- **1:1 실시간 대결 한 판 상한 3,000칩** (`BALANCE.pvpMaxWin`, `capWinPvp`): 사람 대 사람 대결은 더 낮은 상한을 씁니다. 한 판으로 승부가 갈리지 않아 서로 번갈아 주고받으며 균형이 유지됩니다. 이 함수는 우대 여부를 보지 않습니다 — 두 화면이 같은 값을 계산해야 결과가 어긋나지 않기 때문입니다.
- **보유 칩 천장 6,700칩** (`BALANCE.chipCeiling`): 짤짤이로 오래 모아도 총 보유 칩이 이 값을 넘지 않습니다. 천장까지 남은 만큼만 지급됩니다. 조임 구간(4,000) 때문에 차곡차곡 모아 천장에 닿는 길은 사실상 막혀 있고, 4,000 아래에서 한 판 크게 터뜨릴 때만 닿습니다.
- 두 상한 모두 수수료를 뗀 뒤 마지막에 적용되므로 실제로 받는 칩 기준입니다. 8개 게임 모두, 어떤 베팅 조합에서도 적용됩니다. 1:1 대결에서는 두 화면이 같은 값을 아는 테이블 스택으로 천장을 계산해 결과가 어긋나지 않습니다.
- **수수료 5%**: 슬롯·하이로우·룰렛·블랙잭·식보는 승리 시 순이익의 5%를 뗍니다(결과 메시지에 표시). 인디언 포커·홀덤은 자체 레이크 8%, 바카라는 뱅커 커미션(x1.95)이 있어 제외.
- 적용: 슬롯·하이로우·룰렛·식보는 결과 추첨, 바카라·블랙잭은 슈 맨 위 카드 배치, 인디언 포커는 카드 배분, 홀덤은 덱 순서에 적용됩니다.
- 보유 칩 유동성(실측, 고정 베팅 200 · 600세션 · 200라운드): 종료 칩 중위는 슬롯 2,620 · 룰렛 2,730 · 하이로우 2,730, 표준편차는 슬롯 약 1,260 · 룰렛·하이로우 약 330 입니다. 플레이 중 보유 칩은 85% 이상의 시간을 1,500~3,900 안에서 보냅니다(슬롯 87% · 룰렛·하이로우 99%).
- 조정: `BALANCE.target`(범위의 중간값), `squeezeFrom` / `squeezeWinRate`(조임 구간 — `squeezeFrom: 0` 이면 끔), `maxDrawsBelow` / `maxDrawsAbove`(끌어당기는 세기 — 낮출수록 유동성이 커짐), `scaleBelow` / `scaleAbove`(힘이 최대가 되는 거리 = 범위의 폭), `richPeak` / `richDrawsBelow`(파산 가능 조건), `payoutCaps`(배율 상한), `maxWin`(한 판 상한), `pvpMaxWin`(1:1 한 판 상한), `chipCeiling`(보유 칩 천장), `fee`(수수료). `enabled: false`면 끌어당김만 꺼지고 상한·수수료는 유지됩니다.
- `deadZone` 은 0입니다. 넓게 두면 그 구간에서 하우스 엣지에 밀려 목표 아래로 내려앉습니다. 슬롯처럼 엣지가 큰 게임에서 특히 그렇습니다.

## 1:1 실시간 대결 (`js/multiplayer.js`)
인디언 포커와 홀덤은 화면 위에서 **임태현 AI** 와 **다른 플레이어** 중 상대를 고릅니다.

**동작 방식**
- 두 클라이언트가 같은 엔진을 **같은 카드 · 같은 행동 순서**로 돌립니다(록스텝). 서버 없이 Realtime Database 만 씁니다.
- 매칭: `tables/{게임}` 에서 빈 자리가 있는 테이블을 찾아 앉고, 없으면 새로 만들어 기다립니다. 자리 선점은 트랜잭션이라 두 명이 같은 자리에 앉지 않습니다.
- 카드 배분: A석(호스트)이 핸드마다 `hands/{번호}` 에 올리고 B석이 받아갑니다.
- 행동 교환: `acts/{번호}/{순번}` 에 트랜잭션으로 씁니다. 같은 순번은 한 명만 성공하므로, 상대가 자리를 비웠을 때 남은 쪽이 대신 폴드를 밀어 넣어도 충돌하지 않습니다.
- 정산: `settle/{번호}` 트랜잭션을 먼저 잡은 쪽이 **양쪽 계정에 한 번만** 반영합니다. 한 명이 나가도 정산이 빠지지 않습니다.

**규칙**
- 각자 **자기가 가진 칩 그대로** 앉습니다. 입장 최소 100칩(`MP_MIN_CHIPS`). 한 판에 오갈 수 있는 금액은 적은 쪽 스택까지입니다(홀덤은 올인 초과분 반환, 인디언 포커는 베팅 단위 자동 축소).
- 홀덤 1:1 은 **딜러 버튼이 없습니다.** 양쪽이 같은 앤티(BB)를 내고, 먼저 행동하는 쪽만 핸드마다 교대합니다. 블라인드 비대칭이 없어 자리에 따른 유불리가 생기지 않습니다.
- 매 판 끝날 때마다 실제 칩에 즉시 반영되므로, 도중에 나가도 칩이 테이블에 묶이지 않습니다.
- 콜되지 않은 초과 베팅은 정산 전에 돌려줍니다. 상대가 폴드했을 때도 적용되며, 그 금액에는 수수료가 붙지 않습니다. (AI 모드에도 같이 적용)
- **주의**: 보유 칩 전액이 한 테이블에 걸립니다. 한 판에 전 재산을 잃을 수 있습니다.
- 한 번의 행동 제한 시간은 30초(`TURN_MS`). 넘기면 낼 돈이 없을 때 체크, 있을 때 폴드로 자동 처리됩니다.
- 하트비트가 12초(`MP_STALE_MS`) 이상 끊기면 이탈로 보고 자동 폴드 후 대결을 종료합니다.
- 수수료는 AI 대결과 같은 **팟의 8%** 입니다. 사람끼리는 제로섬이므로 하우스 몫은 이 수수료뿐입니다.
- **1:1 균형 조절** (`PVP_BALANCE`, `pvpBalancePlan`): 목표 칩 끌어당김(`balancePlan`)은 제로섬인 1:1 에 쓸 수 없으므로, 대신 **이미 칩이 많은 쪽에게 불리하게 카드를 배분**합니다. 두 사람이 3,000칩 근처에서 주고받게 됩니다.
  - 호스트(A석)만 카드를 만들어 두 화면에 똑같이 내려보내므로 결과가 어긋날 일은 없습니다. 운영 우대가 한쪽에만 걸려 있으면 그쪽이 우선이고, 균형 조절은 그 다음입니다.
  - 적게 가진 쪽에게 가장 유리한 결과를 `k`번 중에서 고릅니다. `k` = 칩 차이 ÷ `scale`(1,500)에 비례하고, 앞선 쪽이 `target`(3,000)을 넘었으면 차이가 작아도 조절이 걸립니다. 차이가 0이면 아무 쪽도 밀지 않습니다.

  | 스택 | 조절 | 밀어준 쪽 승률 (홀덤 / 인디언) |
  |---|---|---|
  | 2,200 vs 2,000 | 없음 (자연 확률) | 48% / 46% |
  | 2,600 vs 2,000 | 적은 쪽 2회 중 채택 | 60% / 71% |
  | 3,200 vs 2,000 | 적은 쪽 3회 중 채택 | 66% / 84% |
  | 4,600 vs 4,400 | 적은 쪽 3회 중 채택 | 66% / 84% |

  - 홀덤은 **플롭 3장만** 고릅니다(홀 카드는 건드리지 않음). 인디언 포커는 카드가 1장이라 조절이 더 강하게 느껴집니다.
  - 차이가 좁혀지면 바로 자연 확률로 돌아갑니다. 실측(인디언 포커 단순 모델, 500쌍): 100~300핸드를 쳐도 두 사람의 칩 차이 중위가 300~370 수준으로 유지됩니다.
  - 두 사람의 **합계는 유지되지 않습니다.** 팟 8% 레이크와 상한(3,000) 초과분이 빠지므로, 오래 치면 둘 다 조금씩 줄어듭니다. 균형 조절은 둘 사이의 차이를 좁히는 장치입니다.
  - 게임 화면에는 표시하지 않습니다. 끄려면 `PVP_BALANCE.enabled = false`, 세기는 `maxDraws`·`scale`·`target` 으로 조정합니다.
- 한 판에 가져갈 수 있는 순이익은 **3,000칩**까지입니다(`BALANCE.pvpMaxWin`). 더 큰 팟을 이겨도 3,000칩만 받고, 보유 칩 천장도 함께 적용됩니다.
  - 상한에 걸린 판은 이긴 쪽이 3,000만 받고, 진 쪽은 자기가 넣은 만큼 그대로 잃습니다(초과분은 지급되지 않습니다). 평균 보유가 2,700 근처이므로 한 판에 상대를 완전히 털어내기는 어렵고, 서로 번갈아 이기며 길게 겨루게 됩니다.

**알아둘 점**
- 카드 값이 데이터베이스에 그대로 올라갑니다. 개발자 도구를 열면 상대 패를 볼 수 있습니다. 축제 운영상 감수하기로 한 부분이며, 막으려면 Firebase 인증이나 Cloud Functions 가 필요합니다.
- `database.rules.json` 에 `tables` 노드가 추가되었습니다. **Firebase 콘솔의 규칙 탭에 다시 게시해야 1:1 대결이 동작합니다.**

## 게임 규칙 안내 (각 게임 화면)
- 8개 게임 화면 하단에 접었다 펼 수 있는 **규칙 패널**이 있습니다. 기본은 펼친 상태이며, 제목 줄을 누르면 접힙니다.
- 담긴 내용: 진행 방식(단계별), 승리 조건과 판정 규칙, 배당·확률표, 지급 한도, 수수료. 인디언 포커·홀덤에는 전략 힌트도 있습니다.
- 표기된 배당은 모두 **베팅액을 포함한 총 지급액** 기준입니다. 배당표 수치는 각 게임 파일의 상수와 일치하므로, 배당을 바꾸면 규칙 패널의 표도 함께 고쳐야 합니다.
- 지급 한도(`BALANCE.payoutCaps`)는 플레이어가 실제로 당첨될 수 없는 조합을 만들기 때문에, 숨기지 않고 테이블 리밋으로 안내합니다. 슬롯·룰렛·식보·바카라 화면에만 표시됩니다.
- 패널 스타일은 `css/theme.css`의 `.rules` 계열입니다.

## 운영 우대 (관리자 페이지)
시연이나 테스트를 위해 특정 계정의 결과를 유리하게 뽑는 기능입니다. **운영진 전용이며 상품 정산에 쓰면 안 됩니다.**

- 관리자 페이지 계정 표의 **우대** 열에서 계정별로 켜고 끕니다. 상태는 `accounts/{id}/boost` 에 저장되고, 켜고 끈 기록은 `chipLog` 에 남습니다.
- 켜면 그 계정의 게임 화면이 값을 실시간으로 받아 즉시 적용됩니다. 끄는 것도 즉시 반영됩니다.
- **게임 화면에는 표시되지 않습니다.** 어느 계정이 켜져 있는지는 관리자 페이지 계정 표의 우대 열에서 확인하세요. 정산 전에 전부 꺼져 있는지 확인이 필요합니다.
- 동작: `balancePlan` 이 후보 8개(`BOOST.k`)를 뽑아 가장 좋은 결과를 채택합니다. 8개 게임 전부에 적용됩니다.
- **홀덤만 플롭 전용**입니다. 홀카드와 턴·리버는 자연 확률 그대로 두고, 플롭 3장만 후보 8벌 중에서 고릅니다(`pickBoostFlop`). 1:1 대결에서는 카드를 올리는 호스트가 처리하며, 우대 대상이 상대일 때도 적용됩니다. 양쪽 다 우대면 아무 편도 들지 않습니다.
- 지급 한도(`payoutCaps`)와 한 판 상한(`maxWin` 4,700)은 우대 중에도 그대로 적용됩니다.
- **우대 중에는 보유 칩 천장(`chipCeiling`)이 적용되지 않습니다.** 그래서 최고 등급(잭팟 7,777)에 도달할 수 있지만, 목표 위에서는 일반 모드와 같은 끌어내림을 받으므로 배율 운과 시간이 많이 필요합니다.
  - 실측: 큰 배율을 노리는 베팅(룰렛 단일번호 4칸 × 250)으로 1,500라운드 × 20세션 중 **4세션만 7,777 도달**. 평범하게 100씩 거는 플레이에서는 400라운드 동안 한 번도 도달하지 못했습니다.
- 실측(베팅 100, 칩 1,000): 룰렛 41% → 99%, 블랙잭 32% → 97%, 슬롯 3% → 26%. 홀덤은 플롭 후 우세 비율 40% → 92%, 프리플롭 우세는 48% → 53%로 거의 그대로.
- 세기는 `js/balance.js` 의 `BOOST.k` 로 조정합니다.

## 칩 지급 / 차감 (관리자 페이지)
- 표의 "칩 지급" 열에서 계정별 +100 / +500 / −100, ± 버튼(직접 입력). 상단 패널에서 사용중·대기·전체 계정에 일괄 지급.
- Firebase 트랜잭션으로 처리되어 플레이 중인 학생 화면의 칩 표시에 즉시 반영됩니다. 0 미만으로는 내려가지 않고, 파산 계정에 칩을 주면 대기 상태로 돌아옵니다.
- 기록은 DB의 `chipLog`에 남습니다. `database.rules.json`에 `chipLog` 규칙이 추가되었으니 Firebase 콘솔의 규칙 탭에 다시 게시하세요(게시 전에는 기록만 생략되고 지급은 정상 동작).

## 관리자 페이지 보안
- 주소를 `admin-7c2e9f.html`로 바꾸고 로그인 화면의 링크를 없앴습니다. 학생에게 노출되지 않게 주소는 스태프끼리만 공유하세요.
- 페이지에 들어가면 관리자 비밀번호를 물어봅니다. 비밀번호는 SHA-256 해시로만 파일에 들어 있습니다.
- 비밀번호 변경: 새 비밀번호의 해시를 만들어(`node -e "console.log(require('crypto').createHash('sha256').update('새비밀번호').digest('hex'))"`) `admin-7c2e9f.html`의 `ADMIN_PASS_SHA256` 값을 교체합니다.
- DB 규칙이 공개 읽기/쓰기이므로 이 잠금은 "학생이 실수로/호기심에 들어오는 것"을 막는 수준입니다. 행사 후 DB를 삭제하세요.

## 칩 흐름 규칙
- 모든 칩 변동은 `updateChips(amount)`(트랜잭션)로만 처리하며, 각 게임은 라운드가 끝날 때 순손익을 한 번에 반영합니다.
- 칩이 0이 되면 계정 상태가 `busted`로 바뀌고 모든 게임 페이지에 파산 오버레이가 뜹니다.
